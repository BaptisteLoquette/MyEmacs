## 1. Multi-Step Agent Workflows for Image Generation (Plan → Sketch → Render → Refine)

### Key Patterns & Techniques

#### Tree of Thoughts (ToT) - Yao et al., NeurIPS 2023
- **Paper**: [arXiv:2305.10601](https://arxiv.org/abs/2305.10601)
- **Repo**: [github.com/princeton-nlp/tree-of-thought-llm](https://github.com/princeton-nlp/tree-of-thought-llm)
- LLM generates multiple "thought" branches, self-evaluates, and backtracks.
- Directly applicable to diagram design: generate multiple layout candidates, evaluate each, select best.
- GPT-4 with ToT achieved 74% on tasks where chain-of-thought only got 4%.

#### Language Agent Tree Search (LATS) - Zhou et al., 2024
- **Paper**: [arXiv:2310.04406](https://arxiv.org/abs/2310.04406)
- **Repo**: [github.com/lapisrocks/LanguageAgentTreeSearch](https://github.com/lapisrocks/LanguageAgentTreeSearch)
- Integrates Monte Carlo Tree Search with LLM-powered value functions and self-reflections.
- Combines reasoning, acting, and planning in one framework.
- SOTA on HumanEval (92.7% pass@1) — demonstrates agent can iteratively generate + evaluate code output.

#### Anthropic's "Building Effective Agents" Patterns (Dec 2024)
- **Source**: [anthropic.com/research/building-effective-agents](https://www.anthropic.com/research/building-effective-agents)
- Six workflow patterns relevant to image generation:

| Pattern | How It Applies to Scientific Image Gen |
|---|---|
| **Prompt Chaining** | Plan → Generate code → Render → Review → Fix |
| **Routing** | Route to specialized renderer (flowchart vs. data plot vs. 3D) |
| **Parallelization** | Generate multiple diagram alternatives in parallel, pick best |
| **Orchestrator-Workers** | Orchestrator breaks complex figure into sub-plots, delegates to workers |
| **Evaluator-Optimizer** | Generate image, LLM evaluates against criteria, iteratively refines |
| **Autonomous Agent** | Full agent loop: user describes figure → agent picks tools → renders → self-corrects |

#### Plan-and-Execute / ReAct Patterns
- ReAct (Yao et al., 2023): interleaved reasoning + action, applicable where agent reasons about visualization then executes code.
- Plan-and-Solve: first create a plan of sub-figures, then execute each.

## 2. Self-Critique and Iterative Improvement Approaches

### Reflexion - Shinn et al., 2023
- **Paper**: [arXiv:2303.11366](https://arxiv.org/abs/2303.11366)
- Language agents with verbal reinforcement learning.
- Agent generates output → receives feedback (scalar or language) → reflects verbally → stores in episodic memory → retries.
- **Application to viz**: agent generates matplotlib code → renders → another LLM call critiques the figure (wrong axis, bad colors, missing legend) → agent reflects and regenerates.
- Achieved 91% pass@1 on HumanEval (GPT-4 baseline: 80%).

### Self-Refine - Madaan et al., 2023
- **Paper**: [arXiv:2303.17651](https://arxiv.org/abs/2303.17651)
- **Demo**: [selfrefine.info](https://selfrefine.info/)
- Single LLM acts as generator, evaluator, and refiner in a loop.
- No supervised training needed — purely test-time improvement.
- Average ~20% absolute improvement across 7 tasks.
- **Application to viz**: same model generates figure code, evaluates the output image (or renders it and inspects), refines code.

### Evaluator-Optimizer Workflow (Anthropic)
- Two LLM calls in a loop: one generates, another evaluates.
- Works best when evaluation criteria are clear (exactly the case for scientific figures: correct data representation, proper labeling, color accessibility, etc.).

### Practical Self-Critique Loop for Scientific Figures
```
User request → Agent generates matplotlib/tikz code → Execute & render → 
Vision-capable LLM critiques the rendered image → Agent fixes code → 
Re-render → Repeat until quality threshold met
```
Key insight: using a **vision model** (GPT-4V, Claude Vision) as the evaluator enables the agent to "see" what it produced.

## 3. Multi-Agent Collaboration for Scientific Figures

### Orchestrator-Workers Pattern
- **Source**: Anthropic "Building Effective Agents"
- Central orchestrator LLM decomposes complex figure request into sub-tasks.
- Worker agents specialize in different figure types (scatter plots, flowcharts, architectural diagrams, LaTeX math).
- Orchestrator synthesizes results into a combined figure or multi-panel layout.

### Parallelization (Sectioning)
- Break figure into independent sub-plots → generate each in parallel → aggregate.
- Example: a 2x2 multi-panel figure where each panel is generated by a separate worker.

### Multi-Agent Debate / Peer Review
- Multiple agents generate different versions of the same figure.
- A "judge" agent (or human) evaluates and selects the best.
- Or: agents critique each other's outputs, iterating to consensus.

### Existing Frameworks
- **LangGraph**: [langchain-ai/langgraph](https://github.com/langchain-ai/langgraph) — stateful multi-agent orchestration. Supports sub-graphs (one per figure sub-plot), checkpointing, human-in-the-loop.
- **CrewAI**: [crewai.com](https://crewai.com) — role-based multi-agent framework. Define "Data Analyst", "Visual Designer", "Reviewer" agents.
- **AutoGen**: [microsoft/autogen](https://github.com/microsoft/autogen) — conversational multi-agent framework from Microsoft. Supports code execution agents.

### Concrete Multi-Agent Figure Generation Pattern
```
Orchestrator Agent
├── Data Analyst Agent     → reads data, suggests plot types, computes aggregates
├── Visualization Agent    → writes matplotlib/plotly code, renders
├── Layout Agent           → handles subplot arrangement, annotations, LaTeX labels
└── Reviewer Agent         → inspects output, checks for data accuracy, suggests fixes
```

### Key Insight: The "Generate Code → Execute → Render → Critique" Loop
The most effective pattern found across all research is:
1. LLM generates code (matplotlib/tikz/mermaid/DOT)
2. Executes code in a sandbox
3. Renders output to an image
4. Feeds image back to LLM (vision model) for critique
5. Iterates

This pattern works because:
- **Code is verifiable** (runs or doesn't)
- **Output is inspectable** (vision model can see errors)
- **Criteria are clear** (correct data, proper labels, good layout)

## 7. Code-to-Diagram & Diagram-to-Code Approaches

### Code-to-Diagram (Text DSL → Rendered Diagram)

This is the mature, battle-tested approach. Agents can generate structured text that gets rendered:

| Tool | Stars | Description |
|---|---|---|
| **Mermaid.js** | ~75k | Markdown-like text to 20+ diagram types (flowchart, sequence, Gantt, ER, mindmap, etc.) |
| **PlantUML** | 12.9k | Text to UML diagrams |
| **mingrammer/diagrams** | 42.2k | Python code to cloud architecture diagrams |
| **Graphviz/DOT** | — | The original text-to-graph engine (30+ years old) |
| **D2** | — | Modern declarative diagramming language |
| **Pintora** | 1.3k | Extensible text-to-diagrams (browser + Node.js) |
| **roadmapper** | 623 | Roadmap as Code (Python) |
| **goadesign/model** | 459 | Software architecture in Go DSL |
| **dbdiag** | 23 | Diagrams as text for concurrent operation histories |
| **hiearch** | — | Hierarchical diagram generator with Graphviz |

### Diagram-to-Code (Rendered Diagram → Source Code)

This is the **harder** direction, less mature:

- **Vision LLMs** (GPT-4V, Claude Vision, Gemini) can describe what they see in a diagram.
- Few dedicated diagram-to-code tools exist.
- Approaches:
  1. Vision model describes diagram components → LLM generates code
  2. Traditional OCR/computer vision extracts shapes and text
  3. SVG parsing (if diagram is SVG) to extract structured data

### Hybrid: Agent Mediates Both Directions

```
Natural Language → [LLM Agent] → Diagram Code (Mermaid/DOT/TikZ) → Render → Image
Image → [Vision LLM] → Description → [LLM Agent] → Improved Diagram Code → Render
```

This bi-directional bridge is where agentic pipelines add the most value for scientific figures.

### "Diagram as Code" Philosophy
- Central idea: diagrams are text files that can be version-controlled (Git), diffed, and reviewed.
- This aligns perfectly with LLM agents that excel at generating and editing text.
- Key repositories tagged `diagram-as-code`: 48 public repos on GitHub.
- Most popular: `mingrammer/diagrams` (42k stars), `plantuml/plantuml` (12.9k stars).

## Summary: Recommended Agent Pipeline Architecture for Scientific Figures

```
┌─────────────────────────────────────────────────────────────────┐
│                     Scientific Figure Agent Pipeline              │
├─────────────────────────────────────────────────────────────────┤
│  1. PLAN                                                         │
│     Orchestrator LLM breaks down figure requirements             │
│     into sub-components (plots, legends, annotations, layout)    │
├─────────────────────────────────────────────────────────────────┤
│  2. ROUTE                                                        │
│     Select best renderer per component:                          │
│     ├── Data plots → matplotlib / plotly / PGFPlots             │
│     ├── Flowcharts → Mermaid / Graphviz / PlantUML               │
│     ├── Math/Equations → TikZ / LaTeX                            │
│     ├── Architecture → mingrammer/diagrams / D2 / draw.io XML   │
│     └── Animations → Manim                                      │
├─────────────────────────────────────────────────────────────────┤
│  3. GENERATE (Parallel Workers)                                  │
│     Each worker agent generates rendering code                   │
│     Code is executed in sandboxed environment                    │
├─────────────────────────────────────────────────────────────────┤
│  4. EVALUATE & REFINE (Iterative Loop)                           │
│     Vision LLM critiques rendered image                          │
│     Agent fixes issues (Reflexion / Self-Refine style)           │
│     Repeat until quality threshold met                           │
├─────────────────────────────────────────────────────────────────┤
│  5. ASSEMBLE                                                     │
│     Layout agent combines sub-figures                            │
│     Generates final multi-panel or composite figure              │
│     Optionally outputs publication-ready format (PDF/TIFF/SVG)   │
└─────────────────────────────────────────────────────────────────┘
```
